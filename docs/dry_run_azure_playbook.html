Azure Dry-Run Playbook

Provision a fresh Ubuntu VM in Azure, install ArionComply end-to-end via Ship 47's install.sh, then validate Ship 48's diagnostic UX by breaking things deliberately.
2026-07-28 · Ship 48'.f · dry-run before real POC
Historical. This playbook documents Ship 48's one-time UX validation exercise, executed with Claude running on the fresh VM. Forward customer engagements use the Customer Prep Checklist (customer preps VM) + CLAUDE_OPERATOR.md (Claude on operator laptop, remote-installs). Preserved here for reference.

What this playbook covers

Two phases:

  • Phase 1 — provision + install (~1h). Fresh Azure VM → running ArionComply, one tenant, one chat, one upload. Green-light for real POC customer.
  • Phase 2 — Ship 48 UX validation (~1h). Deliberately break 4 things, run diagnose.sh against each, paste the bundle into a fresh Claude Code session with CLAUDE_DEPLOY_GUIDE.md, verify the diagnosis lands in seconds.
Two windows recommended — Azure portal in one, this playbook + terminal in another. When the VM is up, you'll be pasting commands via SSH.

Phase 1 · Provision + install

STEP 1~5 min

Create the VM in Azure portal

Portal → Virtual machines → Create → Azure virtual machine.

FieldValue
Subscription / Resource groupyour choice; new RG called arion-dryrun keeps cleanup easy
Regionsame region as this VM (minimize egress + latency)
ImageUbuntu Server 24.04 LTS – x64 Gen2 (matches the demo VM; PostgreSQL 16 + the schema baseline was dumped from 24.04). 22.04 also works if you have a corporate reason to prefer it.

OS diskPremium SSD, 64 GB (default is fine)

STEP 2~2 min

NSG rules — allow SSH + API from your IP only

After creation, the VM has an auto-created NSG called <vmname>-nsg. Edit inbound rules:

RulePrioritySourcePortAction
SSH1000Your public IP/3222Allow
ArionComply API1010Your public IP/328080Allow
Docs (optional)1020Your public IP/328001Allow
Deny all inbound4096AnyAnyDeny (default)

Find your public IP: curl ifconfig.me from your laptop. Never allow Any → 8080 — POC has no auth beyond API keys.

STEP 3~1 min

SSH in + verify OS

ssh arionlabs@<vm-public-ip>
uname -a
cat /etc/os-release  # confirm 24.04 LTS (or 22.04 if you chose that)
df -h /             # ~60GB free expected
free -h             # ~15GB total RAM
STEP 4~2 min

Clone the repo

sudo mkdir -p /data && sudo chown arionlabs:arionlabs /data
git clone https://github.com/jmkamula/RAG.git /data/arioncomply
cd /data/arioncomply
git log -1 --oneline   # confirm HEAD is 3b58b83 or newer (Ship 48 closed)
Private repo? If GitHub asks for credentials, add a deploy key or use a fine-scoped PAT. HTTPS clone with a PAT is fastest for a one-shot dry run.
STEP 5~15 min

Run install.sh

You'll be prompted for 4 passwords — pick memorable ones for the dry run (rotate before real POC).

bash deploy/install.sh

Prompts, in order:

  • Postgres owner (arioncomply) — has RLS bypass
  • Postgres app (arioncomply_app) — RLS-scoped, used by API pool
  • Neo4j (neo4j user) — graph DB
  • OpenAI API key — use a scoped throwaway key — set a $20 monthly cap in the OpenAI dashboard before pasting
Timing — most stages take <30s each. The two slow ones are (a) apt package install (~2 min), (b) Chroma reindex on first API startup (~5-8 min). If install.sh exits before Chroma finishes, that's expected; watch /tmp/arioncomply-chroma.log for "reindex complete".
STEP 6~2 min

Verify services running

sudo systemctl status arioncomply-api arioncomply-chroma --no-pager | head -30
sudo systemctl list-timers 'arioncomply-*' --no-pager
ss -tlnp | grep -E ':(8080|8000|7474|7687) '

Expected: 3 services active (api, chroma, sweep.timer), 4 ports listening.

STEP 7~2 min

Provision the first tenant

cd /data/arioncomply
PYTHONPATH=. python3 scripts/dev/create_tenant.py \
    --name "Dry Run Tenant" --industry technology --admin-email you@example.com

Copy the printed API key into a scratch note — it's hashed at rest, printed once.

STEP 8~5 min

Smoke-test end-to-end

# A. deployment status endpoint (Ship 48)
curl -sf -H "X-API-Key: $KEY" \
  http://127.0.0.1:8080/api/v1/admin/deployment/status | python3 -m json.tool

# B. one chat turn
curl -sf -H "X-API-Key: $KEY" -H "Content-Type: application/json" \
  -X POST http://127.0.0.1:8080/api/v1/chat \
  -d '{"question": "what are our NC findings?"}' | python3 -m json.tool

# C. SPA in browser — through SSH tunnel (safer than exposing 8080)
# Run on your LAPTOP, not the VM:
ssh -L 8080:127.0.0.1:8080 arionlabs@<vm-public-ip>
# Then open http://127.0.0.1:8080/ui/arioncomply.html in your browser

Grant the tenant's key admin:status scope so the endpoint works:

psql "$DATABASE_URL" -c "UPDATE api_keys SET scopes = array_append(scopes, 'admin:status') WHERE 'chat' = ANY(scopes);"
Phase 1 green criteria
  • 3 systemd units active
  • Ports 8080 / 8000 / 7474 / 7687 listening
  • Deployment status endpoint returns valid JSON with all 4 services healthy
  • Chat endpoint returns an answer (may be "no evidence yet" — that's OK)
  • SPA loads at http://127.0.0.1:8080/ui/arioncomply.html

Phase 2 · Ship 48 UX validation

Four break/diagnose scenarios. For each: break the thing, run diagnose.sh, paste the tarball + CLAUDE_DEPLOY_GUIDE.md into a fresh Claude Code session, see if the diagnosis lands.

Fresh Claude Code session per scenario — this is the honest test. Don't reuse a session; each break should be diagnosed by a Claude that has never seen this VM before.
SCENARIO 1~10 min

Chroma down — ARION-BOOT-002

Break:

sudo systemctl stop arioncomply-chroma
curl -sf -H "X-API-Key: $KEY" -X POST http://127.0.0.1:8080/api/v1/chat \
  -H "Content-Type: application/json" -d '{"question":"hi"}' -w "%{http_code}\n"
# Expect: 500

Diagnose:

bash scripts/ops/diagnose.sh
ls -la /tmp/arion-diag-*.tar.gz

Validate: paste the tarball + CLAUDE_DEPLOY_GUIDE.md into a fresh Claude Code session with: "Customer says chat is 500ing. Here's the diagnostic bundle. What's wrong?"

Expected Claude diagnosis: services.txt shows arioncomply-chroma inactive; port 8000 not listening; journal-api.txt shows connection refused on 8000; matches ARION-BOOT-002; fix is sudo systemctl start arioncomply-chroma.

Restore: sudo systemctl start arioncomply-chroma

SCENARIO 2~15 min

Missing PYTHONPATH — ARION-BOOT-005

Break:

# Remove PYTHONPATH from the systemd unit
sudo systemctl edit arioncomply-api  # opens editor
# Add these lines:
#    [Service]
#    Environment=
# The empty Environment= wipes previous settings; save + exit
sudo systemctl daemon-reload
sudo systemctl restart arioncomply-api
sleep 3
sudo systemctl status arioncomply-api --no-pager | head -10
# Expect: failed / activating (auto-restart)

Diagnose + validate — same pattern as Scenario 1.

Expected diagnosis: journal-api.txt shows ModuleNotFoundError: No module named 'rag'; matches ARION-BOOT-005; fix is systemctl edit arioncomply-api to add Environment=PYTHONPATH=/data/arioncomply.

Restore: sudo systemctl revert arioncomply-api && sudo systemctl daemon-reload && sudo systemctl start arioncomply-api

SCENARIO 3~10 min

Fresh tenant, no evidence — ARION-RUNTIME-002

Break: this isn't a bug — it's a fresh-tenant state. Test whether Claude Code diagnoses it correctly.

PYTHONPATH=. python3 scripts/dev/create_tenant.py \
    --name "Empty Tenant" --industry retail --admin-email empty@example.com
# Copy the new key, then:
curl -sf -H "X-API-Key: $NEW_KEY" http://127.0.0.1:8080/api/v1/posture/dashboard | python3 -m json.tool | head -30
# Expect: all controls Not assessed

Diagnose: run diagnose.sh, tell Claude "tenant sees empty dashboard, is this broken or normal?"

Expected diagnosis: tenants.txt shows the new tenant with 0 posture_controls rows; matches ARION-RUNTIME-002; not a bug — expected fresh-tenant behavior; fix is upload evidence or seed via create_tenant.py.

This scenario tests whether the catalog + playbook distinguishes bugs from expected states. If Claude misdiagnoses this as broken, we need to sharpen the language in ARION-RUNTIME-002.

SCENARIO 4~15 min

Bogus OpenAI key — no ARION code yet

Break:

sudo sed -i 's/^OPENAI_API_KEY=.*/OPENAI_API_KEY=sk-bogus-key-fail/' /data/arioncomply/.env
sudo systemctl restart arioncomply-api
sleep 3
curl -sf -H "X-API-Key: $KEY" -X POST http://127.0.0.1:8080/api/v1/chat \
  -H "Content-Type: application/json" -d '{"question":"any NCs?"}' -w "%{http_code}\n"
# Expect: 500

Diagnose: as before.

Expected diagnosis: this is the interesting one. There's no explicit ARION code for LLM auth failures yet — the diagnostic bundle should show journal-api.txt with OpenAI 401s. Claude should recognize the pattern from context and recommend checking OPENAI_API_KEY, but it won't have a stable code to point at.

Follow-up: if Claude diagnoses cleanly without an ARION code, add ARION-RUNTIME-011 or similar to docs/error_catalog.html so future sessions have a stable identifier. This is Ship 48's "codify one code per real incident" rule in action.

Restore: put the real OPENAI_API_KEY back + restart the API.

Success criteria

Phase 1 green if every checkbox from the Phase 1 green criteria (above) is met.
Phase 2 green if:
  • Each of 4 scenarios: Claude Code diagnoses the issue from bundle + playbook alone (no VM-specific knowledge required)
  • Time-to-diagnosis is under 30 seconds per scenario (Claude reads bundle → identifies code → returns fix)
  • Fix commands from Claude actually resolve the issue when pasted
  • The one gap (Scenario 4, missing ARION code) surfaces a real Ship 49 improvement

Cost + cleanup

  • Idle cost: D4s v3 in East US ≈ $140/mo pay-as-you-go. Stop the VM when done to $0 compute; disks cost ~$10/mo.
  • Full teardown: delete the resource group. Everything goes.
  • OpenAI cap: revoke the throwaway key in OpenAI dashboard after dry run. Zero further spend.

Things to note during the dry run

Take notes on these as you go — they feed into Ship 49+ improvements:

  • How long each phase actually took (compare to estimates above)
  • Any prompt in install.sh that was ambiguous or asked for the wrong thing
  • Any error message during install that didn't match an ARION code
  • Anything about the Ship 48 diagnose UX that felt like it needed more or less content
  • Whether CLAUDE_DEPLOY_GUIDE.md was actually helpful to a cold Claude session
