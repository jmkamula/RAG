# Ship 78'.a — union extractor scoping + design

Opens Ship 78'. Direction locked by Ship 77'.f's chaining
experiment: **consensus and critic-verifier are complementary
discovery mechanisms, not competing implementations. Union
captures both paths' unique findings for a real F1 gain.**

## Foundation: what 77' proved

Ship 77'.d ran both paths on the same 5 baseline docs.
Ship 77'.e measured each against ground truth. Ship 77'.f then
measured chaining variants.

Aggregate lenient F1 across 5 docs:
- Consensus alone: 15.2%
- Critic-verifier alone: 19.8%
- **Union: 21.8%** ← chosen direction
- Intersection: 9.5% (high precision, recall crashes)

Per-doc distinct-must overlap (77'.f finding):

| Doc | Consensus musts | Critic musts | Overlap |
|-----|---------------:|-------------:|--------:|
| DPIA | 33 | 10 | 6 |
| RoPA | 46 | 7 | 5 |
| Consent | 39 | 65 | 6 |
| Processor Ops | 24 | 128 | 22 |
| DQA | 24 | 7 | 7 |

Paths hit 5-22 shared musts out of 30-150+ per path. They
explore different parts of the doc-MUST space.

Ship 77'.f's LLM verify-all measurement (Run C) additionally
proved that firing the LLM arbiter on every accept made
consensus WORSE — F1 crashed to 3.5% because the LLM as
prompted rejects legitimate broad statements. LLM as gatekeeper
is over-strict on the acceptance side; it's fine on the
drop-verification side (Ship 34'.c HITL: 20/20 correct
rejects). Different roles, different calibration.

## Design decisions

### D1 — Both paths run always; union outputs

Retire `USE_CONSENSUS_EXTRACTION=1` as a mutual-exclusive gate.
Run both paths on every doc. Union findings.

Rationale (per user pick):
- Ship 77'.f measured +2pp F1 gain; picking single path loses
  it.
- Simplest to reason about: predictable behavior, no per-doc
  routing logic.
- Feature-flagging would require choosing a fair baseline for
  the flag; there isn't one (single-path measurement is what
  we did in 77'.e and it favored critic; but 77'.f showed
  union > critic).

### D2 — Dedup on (control_ref, checklist_item_id)

Two findings are the "same finding" iff:
- Same `control_ref` (e.g. `A.5.18`)
- Same `checklist_item_id` (e.g. `item:A.5.18:review`)

If both paths produce a finding for `(A.5.18, item:review)`,
keep one. Prefer the one with substantive `evidence_text` if
the other's is empty; otherwise keep the first (consensus by
default, since it runs first per D3).

Consequence: if consensus and critic produce different
evidence quotes for the same must, tenant sees the first
one only. Acceptable trade-off — Stage-1 review can surface
both if needed as a follow-on arc.

Not deduping on evidence text: same must with different
supporting quotes IS the same finding for compliance purposes.

### D3 — Execution order: consensus first, critic second, serial

Serial: simpler. No threading/async infrastructure needed.
Failure isolation: one path failing doesn't block the other.

Order: consensus first (currently ~50s), critic second (~60s).
Total: ~110s per doc. 2x current single-path cost.

Rationale:
- Parallel execution would need thread pooling + LLM rate-limit
  management + shared state coordination.
- Serial cost is acceptable per user's "accept 2x cost" pick.
- Total latency ~110s is within the existing pipeline budget
  (docs already take 60-130s for LLM-heavy paths).

### D4 — Emergency kill switch

Keep `USE_CONSENSUS_EXTRACTION` as an env var — but redefine
its semantics:
- Not set / `1` (default post-Ship-78): **union mode** (both paths).
- `USE_CONSENSUS_EXTRACTION=only`: consensus only (Ship 77'.d
  Run A mode; escape hatch for consensus regression debugging).
- `USE_CONSENSUS_EXTRACTION=0`: critic only (Ship 77'.d Run B
  mode; escape hatch for critic-only measurement).

Post Ship 78'.f: retire the env flag entirely unless a real
regression forces its return. Follows the Ship 2'.o precedent
(retire kill-switches once stability is proven).

### D5 — Cost accepted at ~2x LLM per doc

Per user's Q2 pick: quality > cost. Rough per-doc LLM cost:
- Consensus arbiter: batched, ~$0.01-0.03 depending on doc
  size (2000-4000 tokens input × gpt-4.1).
- Critic-verifier LLM refiner: ~$0.02-0.05 per doc (LLM
  emits + critic filters).
- Total: ~$0.03-0.10 per doc union mode.

Tenants pay this ONCE per upload, not per query. Even
1000 doc uploads/month × $0.10 = $100/month LLM cost per
active tenant. Acceptable.

### D6 — Dedup with metadata preservation

The consensus finding and critic finding for the same
`(control_ref, must_id)` may have:
- Different `inference_source` (consensus:fingerprint_match vs
  critic:extracted)
- Different `confidence` (consensus:medium vs critic:high)
- Different `evidence_text`

Retention policy in dedup:
- Prefer confidence: `high > medium > low`
- Tie-break: prefer critic (its LLM refinement is generally
  more thorough evidence extraction)
- inference_source keeps the winner's value
- source_context (Ship 72') adds `dedup_dropped_alternates: N`
  so the audit trail shows the other path also hit this must.

## Risks

**Risk 1** — Serial execution latency. Doc uploads now 2x
slower. Some tenants may hit upload-status polling timeouts.
Mitigation: existing polling has 10-min ceiling; even the
worst-case 130s doc doesn't hit it. Monitor if any tenant's
polling breaks.

**Risk 2** — Consensus produces findings that critic's
subsequent LLM refinement would have rejected. Union preserves
them anyway. Result: MORE FPs from consensus's over-attribution.
Ship 77'.f measured +108 FPs vs critic-alone. Mitigation:
Stage-1 review pipeline catches them; that's what it exists
for. Ship 78' doesn't try to be perfect at extraction — it
tries to be comprehensive.

**Risk 3** — LLM cost spike. If a tenant uploads 1000+ docs in
a burst, LLM cost spikes 2x + hits OpenAI rate limits.
Mitigation: existing rate-limit handling in `rag.llm_client`
retries with backoff; also intake pipeline already queues,
not parallelizes. Impact is latency, not throughput failure.

**Risk 4** — Dedup policy loses evidence detail. When both
paths hit the same must with different quotes, only one quote
survives. Reviewers lose visibility into the alternative.
Mitigation: dedup metadata (D6) surfaces the count. If
material, add a Stage-1 UI element to show alternate excerpts.

## What's parked

- **Ground-truth enumeration gaps** — Ship 77'.f measurements
  are against imperfect ground truth. FP-on-unknown counts
  60% suggests real enumeration gaps. Not blocking Ship 78'
  but future ground-truth iteration would sharpen the
  measurement.
- **LLM gatekeeper prompt tuning** — Ship 77'.f Run C showed
  the LLM is over-strict on accepts. Tuning could make
  consensus+LLM competitive with union alone. Future arc.
- **Intelligent short-circuit** — 77'.f option 3 (skip
  consensus where critic's coverage is dense) — deferred to
  Ship 79'+ if the 2x cost proves prohibitive.
