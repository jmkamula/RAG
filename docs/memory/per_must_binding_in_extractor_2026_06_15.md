[[feedback-phase-1-fallback-masks-gaps]] retired the Phase-1 fallback
in engine evaluation on 2026-06-13. But the doc-side extractor still
emitted findings without `checklist_item_id` — every non-workbook
upload landed unbound. The 2026-06-15 intake-quality work surfaced
the consequence: 13 of 50 recent uploads on Arion were structurally
inert (all findings unbound, can't feed the engine).

Two changes shipped in sequence to close this:

## B — extractor per-MUST binding (307dbdc)

When `_scope_controls_via_doc_mappings` matches a doc_mapping YAML
with `target_leaves`, the extractor now:

1. Saves the deduped target_leaves to `doc.extraction_metrics`
2. Fetches MUSTs for those leaves from Neo4j via
   `_fetch_leaf_musts(leaf_ids)` — driver-cached per-process
3. Injects per-control MUST candidate list into the LLM prompt
   ("Available checklist items per control: …")
4. Updates the response schema — optional `checklist_item_id` field
5. Validates the LLM's id against the per-control MUST set in
   `_parse_llm_response` — hallucinated ids silently dropped (the
   finding stays unbound rather than carrying a bad binding)
6. Persists via `DocumentFinding.checklist_item_id` →
   `posture_writer` INSERT

`_extract_sections` dedup key becomes `(control_ref, checklist_item_id)`
so distinct MUST bindings on the same control no longer collapse.

Legacy fallback path (`doc_mappings_match_count=0`) unchanged —
`leaf_musts` is None, findings stay unbound, as before. Workbook
intake + leaf-scan back-bind paths unchanged.

Test coverage: 4 new cases in `tests/test_extractor_filters.py`
(17/17 PASS):
- valid id retained
- hallucinated id dropped
- legacy path ignores id
- omitted id (LLM correctly omits) → finding still kept

## A — catalog expansion + cap-fanout filter (9f4b7dc)

64 new must_fingerprints catalogs across 16 controls that 12 of the 13
yellow uploads referenced:
- ISMS: 9.2, 7.3, 7.5, 6.1.2, 6.1.3
- People: A.6.4, A.6.5, A.6.6, A.6.8
- Tech: A.8.8
- GDPR: Art.20, Art.24, Art.26, Art.28, Art.32, Art.37

Sub-articles (Art.5.1.x, Art.32.1.x) and pure-derived specs (Art.85)
have no direct leaves — skipped automatically by the generator.

Catalogs generated via `scripts/gen_leaf_scan_catalog.py --control X
--write`. Per [[leaf-scan-catalog-campaign-2026-06-14]] these are
skeleton-quality and benefit from manual review, but the cap-fanout
filter (below) provides a safety net for today's run.

### The cap-fanout problem

Running leaf-scan with the expanded catalog set produced 210
proposals — but inspection showed the autogenerated fingerprints
match too loosely:

| source finding | fanout (MUSTs matched) | reason |
|---|---|---|
| Art.28 — "All third-party vendors…" | 16 | generic supplier prose matches every Art.28 MUST keyword |
| 6.1.2 — "The purpose of this document…" | 9 | preamble matches several risk-assessment MUSTs |
| A.6.4 — "Violations of policies…" | 6 | catches disciplinary register + procedure + scope |

Fanout distribution: 17 sources at fanout=1, 10 at fanout=2, dropping
off through 16. A high-confidence cut: only proposals from sources
with fanout ≤ 1 (each excerpt uniquely identifies one MUST).

`scripts/run_leaf_scan.py --cap-fanout 1`:
- Original: 210 proposals
- After cap: 17 high-confidence proposals
- 6 distinct docs touched
- Dashboard yellow count 12 → 10

Two docs flipped yellow → green from these 17:
- Confidentiality and NDA Policy.docx
- Business Continuity and Disruption Response Plan.docx

## What's NOT solved

- The 10 remaining yellow uploads touch controls whose findings don't
  match any cap=1 catalog. To clear them: catalog refinement (manual
  pass on the 64 autogen catalogs to tighten fingerprints) OR
  re-upload (B now handles binding natively on the second pass).
- Legacy-fallback uploads (no doc_mapping match) still emit unbound
  findings. The structural gap remaining is: write doc_mappings
  YAMLs for the 4 unmatched filename patterns surfaced by
  `/admin/intake/unmatched-patterns`.
