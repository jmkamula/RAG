## Arion role check — amendment to D4

`client_facts` shows Arion is BOTH controller AND processor
(`role_controller=t, role_processor=t, processes_personal_data=t,
eu_data_subjects=t`). This revises design decision D4 which
assumed controller-only + deferred Annex B (processors) to a v2
batch.

Two paths for the tenant to resolve before Phase 2:

- **(a) Ship Annex A only in v1** — Arion sees only controller
  findings for now, Annex B follows in v2 batch. Simpler v1
  scope; delays processor-side visibility.
- **(b) Ship Annex A + Annex B in v1** — full coverage matching
  Arion's actual role profile. Larger v1 curation batch
  (~20 more controls + fingerprints + bridges) but demo tenant
  gets the complete picture.

Neither path blocks Phase 0/1. Resolve before Phase 2 curation
starts.

## Chat behaviour before Phase 2

`is our ISO 27701 (PIMS) posture ok?` currently returns an answer
citing ISO 27001 controls (A.5.34, A.5.10 etc.) that touch
privacy topics. Expected pre-curation behavior — the query IS in
scope for the tenant (has_iso27701=True), but with no 27701
nodes in Neo4j the LLM falls back to the closest ISO 27001
neighbours. This gate flips after Phase 2 loader run.

## Small observation for later cleanup

`scope_loader.inferred_standards` returns THREE GDPR entries when
27701 is enrolled (satisfies + maps_to + implements-via-27001).
Not causing user-visible noise today because `can_evaluate_gdpr`
deduplicates. Worth a dedup pass on inferred_standards for cleaner
scope.describe() output — flag for a follow-up, not blocking.
