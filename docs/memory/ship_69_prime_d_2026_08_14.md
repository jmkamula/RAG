# Ship 69'.d — GDPR stubs + retarget

## What shipped

Ship 69'.a's audit classified 13 bridge edges as `stub_needed`:
curator rationale named a specific sub-clause (`Art.6.4.e`,
`Art.13.2.f`, `Art.28.3.e`, ...) but the target node didn't
exist in Neo4j. Ship 69'.d closes the gap:

1. **12 new RequirementNode stubs created** (Art.28.2 is
   referenced by 3 edges, so 12 unique refs cover 13 edges):
   ```
   Art.6.4.e   Art.8.3     Art.13.2.f   Art.13.3
   Art.15.2    Art.28.2    Art.28.3.d   Art.28.3.e
   Art.28.4    Art.30.1.d  Art.30.1.e   Art.30.2.c
   ```
   Each carries `id / standard_id / ref / title / node_type /
   obligation_type / applies_to / obligation_text / parent_ref /
   chapter / theme`. Verbatim obligation text confirmed against
   Regulation (EU) 2016/679.

2. **13 catalog edges retargeted** — after stub creation,
   Ship 69'.a's audit reclassifies all 13 as `retargetable_now`,
   and Ship 69'.b's `retarget_bridges_69b.py` handles them
   normally. Retargets:
   ```
   A.7.2.2  -[IMPLEMENTS]-> Art.8    → Art.8.3
   A.7.3.3  -[IMPLEMENTS]-> Art.13   → Art.13.3
   A.7.3.10 -[IMPLEMENTS]-> Art.13   → Art.13.2.f
   A.7.4.5  -[IMPLEMENTS]-> Art.6    → Art.6.4.e
   B.8.3.1  -[IMPLEMENTS]-> Art.28   → Art.28.3.e
   A.7.5.2  -[IMPLEMENTS]-> Art.30   → Art.30.1.e
   A.7.5.2  -[IMPLEMENTS]-> Art.15   → Art.15.2
   A.7.5.3  -[IMPLEMENTS]-> Art.30   → Art.30.1.e
   A.7.5.4  -[IMPLEMENTS]-> Art.30   → Art.30.1.d
   B.8.5.2  -[IMPLEMENTS]-> Art.30   → Art.30.2.c
   B.8.5.6  -[IMPLEMENTS]-> Art.28   → Art.28.2
   B.8.5.7  -[IMPLEMENTS]-> Art.28   → Art.28.2
   B.8.5.8  -[IMPLEMENTS]-> Art.28   → Art.28.2
   ```

3. **Ship 59'.e stub roll-down transparently resolves each new
   stub's effective MUSTs** via path 2 (ref-parse to parent
   article). No code change needed — the pattern that Ship 59'.e
   built for the original set of stubs applies unchanged to the
   12 new ones. Bridge writer emits attribution rows targeting
   each stub's own `control_ref` while resolving MUSTs from the
   parent's leaves.

## Codified lesson (extension of 35)

Ship 69'.b's "walk every reader when you change graph edge
granularity" applies again here: the read-side union is
already correct, so adding 12 more stub nodes downstream
doesn't need any reader change. The stub creator + the
retargeter compose into a bounded arc precisely because the
readers were made stub-aware in the prior sub-ship.

Rule: infrastructure that anticipates the topology (Ship 59'.e
stub roll-down; Ship 69'.b's parent-article union) makes
subsequent curation arcs cheap. When Ship 59'.e was written,
it was for a specific set of already-existing stubs; the
generalized ref-parse fallback made it work for the 12 new
ones too, without touching a line of runtime code.
