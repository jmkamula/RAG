## What this is

Phase 3 of the ISO 27701 arc. Phase 2 (three batches) built the
curation catalog. Phase 3 wires the catalog into the runtime
surfaces (chat classifier, LLM prompt, Get Started sequence,
eval).

## Six surgical touches

### 1. SQL flip — queryable-standards gate

```sql
UPDATE standards SET loaded_in_graph = true WHERE id = 'ISO27701:2019';
```

Before: `scope_loader.load_tenant_scope` returned
`queryable=['ISO27001:2022', 'GDPR:2016/679']` for Arion even though
27701 was `direct=['ISO27001:2022', 'ISO27701:2019']`. The
`loaded_in_graph` gate is the queryable-standards filter.

After: `queryable=['ISO27001:2022', 'ISO27701:2019', 'GDPR:2016/679']`
— chat now considers 27701 nodes for retrieval + composition.

### 2. Cross-framework LLM prompt opener

`rag/llm_answer.py` `RANK_AND_ANSWER_SYSTEM.CROSS_FRAMEWORK`:

Before said "GDPR is evaluated via ISO 27701" (legacy — from
pre-Phase-2 when 27701 was aspirational). After says all three
frameworks are first-class citable. Added the framework-role
guidance: 27001 = security foundation; 27701 = PIMS extension;
GDPR = law with Annex D bridge mapping.

### 3. ISO 27701 citation format

Same file, ISO-27701 citation guidance block. Before said "ISO
27701 control 6.11.1" — that would target the §6.x 27002-mapping
clauses. After says "ISO 27701 A.7.2.4" for Annex A + "ISO 27701
B.8.5.6" for Annex B, matching what Phase 2 curated. Also
disambiguated §5.x/§6.x clauses ("ISO 27701 clause 5.4.1.3") from
Annex A/B items.

### 4. Arion primary-framework line

Rewrote to name 27701 as enrolled PIMS + explicit bridge
statement. Chat can now confidently include 27701 posture
alongside 27001 + GDPR without hedging on framework legitimacy.

### 5. Classifier patterns

`rag/classifier.py` `CLEAR_INTENT_PHRASES`:

- Widened existing "iso 2700d posture" patterns to also match
  "PIMS posture" (single alternation: `iso\s*2700\d|compliance|isms?|pims?`).
- Added `(is|are) (our|we) (pims|privacy information management system|iso 27701) (ok|compliant|ready|in place)` → posture_check
- Added `what (is|are) our (pims|privacy information management) (posture|status|findings)` → gap_analysis
- Added direct A.7.x.y / B.8.x.y ref match: `(is|what is) (our)? (iso 27701)? (A.7.[2-5].n|B.8.[2-5].n) (compliant|posture|...)` → posture_check

92 patterns now (up from 89).

### 6. Anchor interleave

`rag/journey/state.py` `_ANCHOR_LEAVES` extended from 20 → 26.
Six 27701 anchors added at natural pairings with 27001 siblings:

- `A.7.2.1` purpose (after ISMS scope + policy)
- `A.7.2.5` PIA (after risk assessment)
- `A.7.3.6` ACR (after access rights)
- `A.7.2.6` processor contracts (after supplier)
- `A.7.2.8` RoPA (before Art.30)
- `A.7.5.1` transfer basis (after Art.30)

Get Started sequence now reads as an interleaved 27001+27701 path
per the design doc's option (c).

### 7. Eval cases (#201, #202, #203)

Three new eval cases at the top of `EVAL_CASES`:

- **#203**: `is ISO 27701 A.7.2.5 compliant?` — direct posture_check
  on a 27701 Annex A ref. Locks first-class-standard integration.
- **#202**: `is ISO 27701 A.7.2.6 (processor contracts) compliant?`
  — most-bridge-fanout control from Batch 1. Locks that primary
  ref surfaces reliably.
- **#201**: `what is our PIMS posture?` — verifies PIMS classifier
  short-circuit + gap_analysis routing.

All three use `must_not_contain` clarify-hedge guards (per the
established minimal-lock pattern). No specific-phrasing locks
that would decay to state drift.
