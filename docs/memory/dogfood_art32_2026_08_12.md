# Auditor journey — Art.32 on Arion demo

## Scope

Walked chat → case-file structured card → dashboard drill-in →
Evidence Package for all 4 Art.32 leaves, reading as an external
auditor examining Arion for GDPR Art.32 compliance. Ship
60–62 shipped bridge attribution across these surfaces; this is
the first end-to-end auditor-perspective read.

## Findings

### CRITICAL — would break audit or actively mislead

**C1. Bridge-attribution excerpts are semantically unrelated to
the target MUST.**

For every ↗ bridged MUST in every Evidence Package, the "Covered
via" section shows an excerpt from the source MUST's
`document_findings`. But that excerpt is whatever the extractor
happened to bind to the source_must_id — not something that
addresses the *target* Art.32 MUST.

Concrete example — `req:Art.32:program_review` MUST "Review date
within the planned interval":
- Covered via _ISO 27001:2022 A.5.18_ (IMPLEMENTS)
  > This includes relevant processes, resources, and environments
  > operated or overseen by Arion Networks s.r.o., such as training
  > laboratories on Azure, as well as applicable operations from
  > remote locations.
  > From _1 ISMS-Scope.docx_
- Covered via _ISO 27001:2022 6.1.2_ (GOVERNANCE)
  > - Risk assessments will be conducted regularly to identify and
  > mitigate security risks.
  > From _Information Security Policy.docx_

An auditor reads: "You claim A.5.18 covers Art.32's *review date
within planned interval* — but you show me an ISMS scope
statement about training labs on Azure. That's not the same
thing."

This is **worse than showing no attribution at all** — it creates
the false impression that Arion has evidence that specifically
covers the target MUST when the shown evidence addresses a
different topic entirely.

**Root cause**: Ship 62' fetches the first available excerpt for
each source_must_id, no semantic-fit check between source-MUST
topic and target-MUST topic. The bridge relation (A.5.15
IMPLEMENTS Art.32) is a control-level statement; the specific
excerpt bound to a specific source_must_id is not.

**Fix shapes** (need product/design call):
- Suppress the excerpt block when the source excerpt's semantic
  distance from the target MUST text is above a threshold.
- Reframe the excerpt as "example evidence Arion has on the
  source control" instead of "this is how Art.32.<x> is covered."
- Cap attribution to the ref only ("Covered via A.5.18 IMPLEMENTS")
  and drop the excerpt entirely if we can't confidently show
  target-relevant text.
- Cross-reference the source_must_id's own MUST text against the
  target's MUST text; only show excerpt when the source MUST is
  semantically about the same topic.

### HIGH — would confuse the auditor's understanding

**H2. Chat prose recommends remediating physical controls on a
cloud-only tenant.**

Chat says:
> Address gaps in ISO 27001 A.5.23, A.7.7, A.7.8, A.7.9, A.7.10,
> A.7.11, A.7.12, and A.7.13, as these directly implement GDPR
> Art.32.

A.7.7–A.7.13 are physical controls (clear desk, physical entry,
cabling, etc.). Arion is cloud-only per CLAUDE.md and its
`client_facts`. Those controls should be N/A for Arion, and the
LLM shouldn't recommend remediating them.

Ship 60' documented that `tenant_must_overrides` + case-file
digest give the LLM correct N/A signals per-MUST. But the LLM's
top-level prose is still enumerating N/A refs as if they need
remediation. Either the digest isn't surfacing "these controls
are N/A for this tenant" prominently enough, or the LLM is
ignoring that signal on cross-framework rollups.

**Real-world consequence**: auditor thinks Arion has a fleet of
physical premises. Or Arion's compliance team goes off to
"implement" clear-desk policies on 100% remote staff.

**H3. Chat prose numbers contradict internal counts.**

Intro: "Currently NC — none of the 9 required items are fully
present."
Primary card: "0 of 4 required items present (3 with partial
evidence)."
Drill-in: 6 of 16 MUSTs bound across 4 leaves.

Where does 9 come from? Not 4 (leaves), not 16 (MUSTs), not 10
(unmet MUSTs). Likely an LLM hallucination on the arithmetic.

Auditor: "Is it 9 elements missing or 4? Which document should I
believe?"

**H4. Chat prose doesn't leverage the bridge attribution we
built.**

Ship 60'.j put `(N/M MUSTs bridge-covered)` in the digest so the
LLM could narrate coverage. Ship 60'.h attempted (dead) to add a
prose nudge. But the visible chat output still tells a "your ISO
controls are ALL NC, remediate them all" story — not "your ISO
work covers 10 of Art.32's 16 required elements, focus
remediation on the 6 gaps."

Structured card has the data (`n_bridged: 4, 2, 1, 3`); the LLM
prose ignores it. Bridge attribution reaches the case-file card
+ Evidence Package but NOT the chat answer text.

**H5. Evidence Package excerpts still show Markdown-escape
residue.**

`Information Security Policy.docx` excerpt:
> - Risk assessments will be conducted regularly to identify and
> mitigate security risks\.

The trailing `\.` is Markdown escape leaking through. Ship 8'.a
backfilled these but the extractor's writer must still be
introducing them on new intakes.

### MEDIUM — reads poorly but auditor can figure it out

**M1. `Reviewer identity` MUST attributes to an incident-response
excerpt.**

`req:Art.32:program_review` MUST "Reviewer identity (DPO + CISO +
Risk lead)" is direct-satisfied (✓). The bound excerpt:
> Revoke affected credentials via Azure AD
> - Initiate scan using Defender for Endpoint
> - Notify users via Signal or SMS
> - Restore from last known clean backup

That's an incident-response playbook, not a description of who
performs Art.32 reviews. Extractor binding is wrong. Auditor
would say: "You claim this is your Art.32 reviewer identity
evidence, but it's your incident-response runbook."

This is different from C1 (which was about bridge attribution
mis-mapping): here the DIRECT extraction bound a wrong excerpt
to the MUST id. Root cause is upstream in the intake / extractor.

**M2. 53 implementing controls with no prioritization.**

Chat says "Showing 8 of 53 — see all in the dashboard for
Art.32." No auditor knows where to start. The list order looks
alphabetical-ish (A.5.10, A.5.11, A.5.18, ...) which is
uninformative. Could be ranked by (a) MUSTs unmet on the
implementer, (b) bridge fanout, (c) posture severity.

**M3. Evidence Package "Recommended additions: 0 of 1 covered"
noise.**

Appears in every leaf, mostly meaningless since SHOULDs aren't in
SSoT (Ship 61 deferral). Auditor gets used to ignoring it, but
the line is noise.

**M4. "0 of 4 required items present (3 with partial evidence)"
mixes leaf-count with MUST-count semantically.**

The 4 is leaves; the "partial evidence" is at MUST level within a
leaf. Reader has to work out the granularity mismatch. Same
across chat, structured card, drill-in.

### LOW — cosmetic

**L1. Bridge attribution says "ISO 27001:2022, ISO 27701:2019
controls".**

Should be "ISO 27001:2022 or ISO 27701:2019 controls" — with an
"or"; comma alone reads as a list, which is fine but slightly
unclear on 1-element attribution ("1 element is covered by
evidence for related ... controls" — plural noun on single
element is grammatically wrong when there's just one bridged
element and just one standard).

**L2. Same 4 excerpts appear across all 4 leaves of the same
control's Evidence Packages.**

Every bridged MUST across all 4 Art.32 leaves shows the same 3
excerpts (from A.5.18 + 6.1.2 + A.5.1). Each package is
generated independently so Ship 62's dedup doesn't cross
packages. Auditor reading the 4 packages in sequence sees the
same evidence quoted 12 times. Low priority because the packages
are single-use artifacts; but multi-leaf audit prep would benefit
from cross-package dedup.

**L3. Test Log leaf: `src_docs=0` + `n_bridged=3` reads
contradictory.**

"You have no source documents on the test log" + "3 elements
covered via cross-framework" is technically consistent but reads
weird without knowing the model. Might be worth relabelling.

- **HIGH**:     4 (H2 N/A control leak, H3 numeric contradiction,

## What this means for the next arc

The Ship 60–62 arc's biggest weakness surfaced by this walk is
**C1**: bridge attribution's excerpts are semantically wrong.
Fixing this well is a real product design question, not a code
tweak:

- Are we saying "your ISO A.5.15 rbac evidence LITERALLY
  addresses Art.32's approval MUST" (semantic fit required)?
- Or "your ISO A.5.15 rbac evidence is thematically nearby, use
  it as a starting point for authoring Art.32 evidence"?

The former is auditor-defensible, the latter is a work-planning
nudge. The current UX conflates them.

**H4** is the second-biggest miss. We built the bridge attribution
layer + shipped it across five surfaces — but the chat prose,
which is arguably the highest-traffic surface, doesn't tell the
"you're not as far behind as you look" story. That story is what
the whole SSoT + bridge arc was building toward.

**Recommendation for the next real arc**: C1 first (auditor-
correctness), then H4 (chat prose reflects the attribution we
built). H2 is important but rides on a broader "N/A handling in
LLM prose" story that's its own arc.

No code changes made in this walkthrough — punchlist only, as
requested.
