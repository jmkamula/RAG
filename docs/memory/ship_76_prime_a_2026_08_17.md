## Blast radius ordering

1. **External API endpoints** (highest). Partners + auditors are
   the audience for `/api/external/v1/posture/*`. Rendering N/A as
   if assessed misrepresents scope in an auditor-facing surface.
2. **Dashboard heatmap**. Tenant-facing; N/A cells muddy the "what
   am I being assessed on" question.
3. **Casefile leaks** (build_related_cards + xfw_bridges +
   demonstrated_by). Prose leaks into tenant chat answers; case #5
   trips stochastically.

## Design decisions

### D1 — CaseFile.in_scope(ref) is the SSoT predicate

Add method to `rag/casefile/types.py`:

```python
def in_scope(self, ref: str) -> bool:
    """True iff the ref is in-scope for this tenant.

    Ship 66'.a SSoT: posture_controls.applicability_status.
    Missing rows treated as in-scope — a ref not in posture_controls
    is either unassessed but applicable, or not curated at all.
    Only explicit applicability_status='na' drops.
    """
    rec = self.posture_for(ref)
    if not rec:
        return True  # unassessed but not scoped-out
    return rec.get("applicability_status") != "na"
```

One implementation, N call sites. Any future scope-truth change
touches this method only.

For API + dashboard sites that don't have a CaseFile in scope, add
a mirror helper in `rag/posture/scope.py`:

```python
def is_ref_in_scope(pg_conn, tenant_id: str, ref: str) -> bool:
    """SSoT predicate for callers without a CaseFile. Same rule as
    CaseFile.in_scope but reads posture_controls directly."""
```

Both delegate to the same predicate shape — one column, one rule.

### D2 — Per-site policy (hard vs soft)

Same predicate, different actions per surface:

**Hard filter** (drop N/A unconditionally):
- Dashboard heatmap
- External `/posture/{ref}` detail endpoint (→ 404)
- Digest `_render_xfw_bridges` (bridge lines referencing N/A
  primary controls)
- Digest `_render_demonstrated_by` (N/A demonstrators)

**Soft filter** (drop N/A unless LLM cited — Ship 66'.c grounding
rule):
- `build_related_cards` — if LLM voluntarily named an N/A ref in
  intro/actions, render a grounding card so the mention has an
  anchor. Auto-injected demonstrators + cross-role neighbors that
  are N/A drop.
- External `/posture` bulk endpoint — soft with opt-in flag (D4).

**No change** (already correct):
- Digest OBLIGATIONS (soft-filter policy, Ship 66'.c)
- Digest POSTURE section (D5 migration only — behavior unchanged)

### D3 — External API 404 semantics for N/A refs

`GET /api/external/v1/posture/{ref}` currently returns the row for
an N/A ref. Post-76' returns 404. Rationale: the ref is scoped out
for this tenant; from the partner's perspective, "this control
isn't in your scope" is a legitimate 404. Alternative considered:
200 with a scope-out indicator. Rejected — 404 is cleaner + matches
how partners think about inventory.

OpenAPI schema post-76'.d: document the 404 explicitly with a
scope-out response shape (structured error `code: "control_out_of_scope"`).

### D4 — Bulk endpoint: filter by default, opt-in for N/A

`/api/external/v1/posture` bulk endpoint filters N/A by default but
exposes `?include_na=true` for callers that need scope-out
visibility (compliance auditors reviewing what was excluded). Same
model as the OBLIGATIONS digest section (soft-filter with grounding
carve-out) but at API surface.

### D5 — Retire `finding == "N/A"` scope checks

The 1 FINDING-CHECK site (`_rank_posture_refs`) works today because
data mirrors, but if a future change ever wrote
`applicability_status='na'` independently of `finding` (or vice
versa), it would drift. Migrate to `cf.in_scope(ref)` for
consistency. Zero behavior change today.

### D6 — One sub-arc per surface family, dogfood per sub-arc

Same discipline as Ships 74/75 — audit → per-surface migration →
retro. Fine-grained sub-arcs surface divergences early.

## Risks

**Risk 1** — External API 404 is a contract change. Partners may
have code that expects 200 for any posture ref. Mitigation: 404
matches how partners think about inventory; document explicitly in
OpenAPI + SDK README. Not a version bump since it's a correctness
fix rather than a breaking API redesign.

**Risk 2** — Dashboard heatmap visual change. N/A cells currently
render as small tiles in theme buckets; post-76'.d they disappear.
Auditor might miss the visibility of "here's what was scoped out."
Mitigation: dashboard already has a scope-out summary panel elsewhere
(from the dejargonize pass); direct auditors there. Verify the
scope-out summary is still complete before shipping 76'.d.

**Risk 3** — `build_related_cards` soft filter needs care around
the grounding rule. Test: an eval case where the LLM VOLUNTARILY
names an N/A ref should still get a card so the mention has an
anchor. Add this positive test to 76'.c dogfood.

**Risk 4** — `_render_xfw_bridges` "hard filter" might over-drop
in edge cases where an N/A primary control is legitimately named
in a bridge line (e.g. auditor query about a specific N/A control).
Consider: policy is "hard drop N/A primary refs from AUTO bridge
lines; still render if the LLM/user cited the N/A ref." Same soft-
filter shape as `build_related_cards` for consistency. Revisit in
76'.c during implementation.

## Codified lesson candidates (for the retro)

- **SSoT-introduce != SSoT-cascade.** A schema column with a rule
  enforced at 3 critical points is a strategic enforcement, not an
  exhaustive one. Every consumer that reads the underlying data
  needs the rule applied — an audit-and-cascade sub-arc closes the
  gap systematically.
- **Grep for the predicate.** Ship 76' audit found the leaks by
  greping every reader of `posture_controls` / `posture_by_ref()` /
  `posture_for()` and cross-referencing with sites that check
  `applicability_status`. The delta was the LEAK set. Cheap audit
  shape.
