# Ship 69'.a — Bridge rationale audit

## Purpose

Ship 68'.b retired the fake per-MUST coverage claim across every
tenant-facing surface. The remaining honest question is: *how much
of the bridge catalog could truthfully be retargeted at a narrower
scope?* Ship 69'.a measures it.

## Method

`scripts/curation/audit_bridge_rationale.py` reads every
IMPLEMENTS/SUPPORTS/ENABLES/GOVERNANCE edge in Neo4j, parses each
`e.rationale`, and classifies the edge into one of four buckets:

- **A. retargetable_now** — rationale cites a specific sub-clause
  (`Art.X.Y[.z]` / `A.N.M.k` / clause `N.M.k`) AND that node exists
  in Neo4j. Can be re-pointed with zero data-model change.
- **B. stub_needed** — rationale cites a specific sub-clause BUT
  the node doesn't exist. Needs Ship 59'.e-style stub creation
  first, then retarget.
- **C. dimension_metadata** — rationale names a security dimension
  or mechanism (confidentiality / integrity / availability /
  encryption / pseudonymisation / access control / processor /
  accountability / etc.) but no sub-clause. Needs dimension
  metadata on the edge, not retargeting.
- **D. unspecified** — rationale is genuinely whole-source →
  whole-target. Stays whole-to-whole; the Ship 68'.b honest
  reframe is the correct UX.

Full per-edge output at `results/bridge_rationale_audit.csv`.

`IMPLEMENTS` carries almost all retargeting potential — 47 of the 50
retargetable edges land there. That tracks intuition: an "X
implements Y.Z.a" rationale is the shape most likely to name a
sub-clause. `SUPPORTS` / `ENABLES` mostly cite dimensions or
whole-to-whole rationales. `GOVERNANCE` is dominated by
accountability-dimension edges (12 of 14).

## Decisions for the follow-on arcs

**Ship 69'.b — retarget 50 IMPLEMENTS edges** (no schema change,
data-only). Estimated: ~30-45 min of curator work + a validation
script. Highest-value slice: A.5.18 → Art.32.1.b, A.5.24 →
Art.32.1.d, A.5.29 → Art.32.1.b, etc. Retargeting means the
existing SSoT + bridge writer immediately reflects narrower
attribution in the Evidence Package's ↗ blocks, without any UX or
schema change.

**Ship 69'.c — dimension metadata**. Add optional `dimensions`
property on bridge edges; 168 edges get non-empty lists. Rationale
parser already extracts them (audit script). UX reframe: *"asserted
implementation of the {dimension} aspect of Art.X via A.Y — see
rationale."* Larger arc; schedule after 69'.b lands.

**Ship 69'.d — 13 stub creations**. Small; folds into the tail of
69'.b or its own micro-arc. Requires: node creation via
enrichment/documents/load_to_neo4j.py extension (mirror of
Ship 59'.e stub roll-down), then retarget the 13 edges.

**221 unspecified edges — leave alone**. Ship 68'.b's reframe is
already the correct UX for these. No follow-on work.

## Codified lesson

### 34. Audit before refactoring; refactor before schema-changing

The temptation after Ship 68'.b was to jump to "let's build the
sub-clause retargeting refactor" without knowing how many edges
would actually benefit. The audit says only 50 edges (11%) are
one-hop retargetable and another 13 (3%) need small stub work.
The remaining 89% either need dimension metadata (larger arc) or
are honestly whole-to-whole and don't want touching.

That's a very different plan from "refactor all 452 edges." The
audit script is 200 LOC and answered the scoping question in one
afternoon, saving weeks of speculative refactor scope.

Rule: when a candidate refactor targets a large uniform data set,
write the classifier before writing the refactor. The distribution
usually tells you the refactor is smaller than you thought — or
larger, in ways you didn't anticipate.
