# Ship 69'.c — Dimension aspects in Evidence Package UX

## What shipped

Ship 69'.a's audit found that ~45% of bridge edge rationales
(202 of 452, post-69'.b+69'.d retargets) name a specific
security dimension — *confidentiality*, *integrity*,
*availability*, *encryption*, *access rights*, *processor*,
*accountability*, *risk assessment*, etc. — that the curator
asserts the mapping addresses.

Ship 69'.c surfaces those dimensions in the Evidence Package
UX as a **group-level italic prose sentence** under each ↗
MUST label:

```
- ↗ **Review date within the planned interval** (asserted implementation via related controls)
  _Related controls address access management, confidentiality, availability, and incident response._
  ↳ Asserted implementation via _ISO 27001:2022 A.6.3_ (IMPLEMENTS, confidence: HIGH)
    Rationale: Information security awareness, education and training
    ensures staff processing personal data understand their obligations.
    _ISO 27001:2022 A.6.3_ posture: **OFI** (22 of 23 MUSTs satisfied)
    ...
  ↳ Asserted implementation via _ISO 27001:2022 A.5.18_ (IMPLEMENTS, confidence: HIGH)
    Rationale: Access rights management implements Art.32.1.b
    ongoing confidentiality of processing systems.
    ...
```

The tenant reads the italic line and instantly knows *what
aspect* of the target MUST the related controls address —
without having to read every rationale block below.

## Where this lives

- `rag/output/dimensions.py` — a 130-LOC compute-at-read-time
  module:
  - `_DIMENSION_MAP` controlled vocab (~35 raw tokens → 22
    display terms). Curator variants collapse: "access
    control" + "access rights" + "authorisation" all →
    *access management*.
  - `extract_dimensions(text)` — regex + normalize + dedupe.
  - `aggregate_dimensions([rationales])` — merge across a
    group, cap at 4 (past 4 the sentence starts to feel like
    a keyword dump).
  - `humanize_dimension_list(dims)` — natural prose with
    Oxford comma ("A, B, and C").
  - `summary_sentence(rationales)` — full UX sentence, or
    `""` when no rationale in the group carried a
    recognized token.
- `rag/posture/evidence_package.py` — imports
  `summary_sentence`; injects the italic line right after
  the ↗ MUST label. No other renderer touched this ship.
- `tests/test_evidence_package.py` — assertion added to
  `test_bridged_leaf_shows_cross_framework_header`:
  `"_Related controls address " in required`.

Zero schema migrations, zero loader changes, zero
`bridge_coverage` writer changes. Aligns with Ship 7'
principle: *opt-in, never middleware*.

## Design decisions

**Compute-at-read-time over persisted metadata.** Rationale
parsing costs microseconds per bridge; the audit script has
already validated the token set covers ~45% of edges. Adding
a schema column + loader hook + `BridgeSource.dimensions`
field would be ~3× the work for the same visible UX. If
future consumers need to filter by dimension (e.g. "show me
all my confidentiality-related bridges"), that's when the
persistent variant becomes the right investment.

**Group-level, not per-source.** The dimensions come from
the collected rationales for this MUST, aggregated. Showing
per-source dimension tags would repeat what the rationale
already says (curator rationales embed the dimension in
prose). The group-level summary tells the tenant WHAT the
MUST's cross-framework attribution centers on — a
character-level bootstrap that the per-source rationales
then elaborate.

**Vocab normalization.** Curator variants collapse to fewer
display terms. "access control" / "access rights" /
"authorisation" all → *access management*. Reader sees a
consistent term set regardless of which curator authored
which rationale.

**Silent when nothing to say.** ~50% of MUSTs have no
recognized dimension tokens across their bridges. Those
MUSTs render exactly as before (Ship 68'.b) with no italic
line. Additive, not disruptive.

## Codified lesson

### 36. Read-time parse before schema

The natural default for feature work like this is "add a
column, wire the writer, wire the reader." But for
enrichment that lives ENTIRELY inside existing curator
prose, a read-time parser is faster to ship AND cheaper to
iterate on. Vocabulary changes are a one-file edit; column
changes are a migration + backfill + retest.

Rule: when a feature just needs to *extract* structure
from data already present, ship the parser first. Only
persist the extracted structure once a consumer needs to
query or filter on it — not just render it.
