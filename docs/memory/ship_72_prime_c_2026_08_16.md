# Ship 72'.c — xlsx + workbook migrated

## What shipped

### `_extract_templated_xlsx` (extractor.py:894) — 2 sites migrated

The xlsx templated fast-path had TWO DocumentFinding construction
sites:
1. Per-column register bindings (~line 902)
2. Per-doc-field bindings (~line 932)

Both now emit `ExtractedCandidate` objects through
`FINDING_CONTRACT.bind()`. The empty-column check
(`col_has_data[i]`) that used to gate the register-column loop is
replaced by the contract's `EMPTY_TEXT` check: pass an empty
`excerpt_text` and the contract drops it. Same for the doc-field
loop's `if not content: continue` gate.

Net effect: xlsx now benefits from the contract's `catalog_recognises`
check (mapping YAML typos in column item_ids drop with a warning
instead of silently binding to a nonexistent MUST).

### `workbook_persistence._findings_for_pass` — catalog check added

Workbook writes SQL directly to `document_findings` (bypasses the
`DocumentFinding` dataclass), so it doesn't route through
`FINDING_CONTRACT.bind()` at the object level. But the same domain
rules apply — a mapping YAML typo in a MUST id would silently
insert a bad `checklist_item_id` and the SSoT reader would drop it
on lookup with no trail.

Fix: `_findings_for_pass` now calls `catalog_recognises` per
`must_id` from `pass_prop.satisfied` / `partial`. Unknown ids get a
WARN + skip. Same defensive posture as Task #606 templated path.

Not routing through `FindingContract.bind()` here would be pure
ceremony — workbook excerpts are always `sheet 'X' col 'Y'` strings
(never scaffolding), and control_ref + standard_id come from the
proposal metadata rather than being derived. Applying the ONE rule
that actually differs (catalog check) inline keeps the workbook
path simple.

## Design note — when to route vs when to inline

The contract is the SSoT for extractor domain rules. Extractors
consume the SSoT either by:

- **Routing** — build an `ExtractedCandidate`, call `.bind()`, use
  the returned `DocumentFinding`. Right shape for extractors that
  operate on natural-language text where scaffolding recognition
  matters (templated markdown/docx, LLM output).
- **Inlining specific predicates** — call `catalog_recognises` or
  `is_scaffolding` directly. Right shape for extractors whose data
  shape doesn't need every rule the contract applies (workbook
  SQL-direct writes, tabular data where excerpts are metadata refs).

Both are valid uses of the SSoT. The rule that matters is: **the
predicate implementations live in ONE place**. As long as `catalog_recognises`
is defined in `finding_contract.py` and imported everywhere else,
adding a new domain rule is a one-file edit.

## Deterministic paths NOT migrated

Three sites still construct `DocumentFinding` directly:

- `_extract_via_consensus` (extractor.py:362) — Ship 33+ consensus
  engine.
- `_run_critic_verifier_pass` (extractor.py:546) — post-extract
  verifier that may promote candidates.
- `_extract_via_fingerprints` (extractor.py:3525) — deterministic
  fingerprint-based extraction.

All three have their own local catalog + shape checks that predate
the contract. Same migration shape as 72'.b/c but they're
lower-frequency + deterministic; folding into a future sub-ship
(72'.f or later) is fine. Metrics + snapshot tests in Ship 72'.d
will surface any drift.
