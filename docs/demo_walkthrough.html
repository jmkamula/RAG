Act 1 — The architecture brief 60 sec

Show architecture_brief.html. Scroll to the ASCII diagram — point at the four layers: Surfaces → Case-file discipline → Consensus → Role-aware graph.
This is a compliance program ledger, not another evidence repository. We track where evidence lives, its freshness, its ownership. Tenants keep sovereignty in the systems they already run — Odoo HR, Okta IAM, ServiceNow CMDB. Under the hood it's a cross-platform RAG stack purpose-built for compliance. Everything's traced end-to-end. Let me show you.

Act 2 — Chat 3 min

Demonstrates: Case-file discipline (Ship 2') 7-signal consensus (Ship 1) Role model (Ship 40) Chat persistence (Ship 46)

Query 1: "our top NC findings on access control?"

Type in chat, hit Enter. Response ~3-4s (deterministic short-circuit).
This answer bypasses the LLM entirely. Posture data is authoritative — NC/OFI counts, cited refs, links back to the dashboard. Note the [DRAFT] tags on unconfirmed postures.

Query 2: "how do we close the A.5.15 gap?"

Response ~6-8s (LLM path via case-file).
The LLM gets a compact digest — query, posture, cited refs, cross-framework bridges — ~650 tokens vs the pre-Ship-2' 21k-token average. It composes prose, then a deterministic preservation-check verifies every required ref, [DRAFT] tag, and verdict prefix is present. Missing elements get appended in a footer — never rewriting LLM prose. The LLM cannot silently drop compliance-load-bearing facts.

Query 3: "what about DPIAs?"

Deictic follow-up — uses last_entity from prior turn. Classifier routes to cross_framework. Point at the bridges footer: "↳ Bridges to ISO 27001 for Art.35: ..."
This is the framework role model. GDPR is an obligation framework; ISO 27701 is an extension that DEMONSTRATES many GDPR articles; ISO 27001 is the program underneath. When you ask about DPIAs, we walk the DEMONSTRATES edges and cite both frameworks with proper role semantics.

Click a chat-link → drill-in

URL bar shows #dashboard?control=A.5.15 — no page reload. Detail panel opens immediately with canonical title, engine verdict reason, per-leaf breakdown. Then click Chat nav back — conversation still there.
Deep-link into any control from chat. Chat state persists across navigation — localStorage-backed session_id means the server-side conversation context also survives page reload.

Act 3 — Dashboard 2 min

Demonstrates: Framework role model DEMONSTRATES overlay Engine verdict computation

Point at the framework-tabbed heatmap

ISO 27001 / ISO 27701 / GDPR tabs. Colours: red NC, amber OFI, green Comply, grey Not assessed.
This tenant is mid-cycle assessment — 88 NC, 12 OFI on ISO 27001. What you're looking at is a struggling tenant. The tool's job is to help them close gaps, not to make the numbers look green.

Click a cell — say A.5.34 (privacy protection, ISO 27001)

Detail panel shows canonical title, obligation text, engine verdict reason ("0 of 4 leaves satisfied"), per-leaf breakdown with ✓/○ markers, cross-role neighbors section (ISO 27701 A.7.2.5 extension + Art.24 obligation).
The engine evaluates every curated multi-leaf spec. Here it says "0 of 4 leaves satisfied" — we see which specific leaves are missing evidence. The cross-role section shows the DEMONSTRATED_BY overlay: if we satisfy the ISO 27701 extension leaves, this control's evidence auto-materialises.

Point at cite freshness card / cascade KPIs (if any)

If the tenant is using cited evidence — pointers into Odoo or Okta rather than uploaded docs — this card tracks verification cadence. Auditors want to know when evidence was last reconciled.

Click into an existing document → Evidence Package

Markdown-rendered coverage summary: "Fully covered — 7 of 7 required elements covered (100%)". Per-MUST breakdown. Guidance citations (ISO 27002 §5.15, etc.).
This is what an auditor sees for one document's coverage of one leaf. Every claim has a provenance. If you upload a docx or xlsx via our templates, we auto-approve the findings because the tenant authored them; anything the LLM extracts goes through Stage-1 HITL review first.

Explain the two-view semantics briefly

This is Ship 42's contribution. Engine reads one row per MUST for its checklist_item_id = ANY(...) query — needs N rows for N MUSTs to compute the verdict. Auditor UI wants 1 row per unique excerpt-plus-control-ref for a clean citation view. Same table, two views, via an evidence_group_id column stamped at write time and DISTINCT ON at read time. 60% reduction in queue visual size on this tenant.

Act 6 — Observability 3 min

Demonstrates: Dual-backend OTel (Ship 44) GenAI semconv N+1 fix (Ship 45)

Switch to Jaeger

Service: arioncomply-api. Operation: POST /api/v1/chat. Find Traces. Click the most recent chat trace.

Show the waterfall

  • Root: POST /api/v1/chat — full request
  • classify node — ~3s
  • retrieve node — ~3.5s (after Ship 45's N+1 fix; was 7.7s pre-fix)
  • Inside retrieve: arion.resolver.resolve, arion.resolver.vector_search, arion.resolver.graph_expand, arion.answer_augment.build_related_cards
  • LLM call: gen_ai.chat.rank_answer
Every request is a trace. Every LangGraph node, every DB query, every LLM call. Auto-instrumentation via OpenInference for the LLM stack — traces conform to the OTel Semantic Conventions for GenAI, so they're portable to Grafana Tempo, Honeycomb, Langfuse, any OTel-native tool. Custom arion.* spans wrap our proprietary bits: consensus signals, engine verdict computation, case-file digest, preservation-check.

Switch to Phoenix

Click the same trace or a recent one. Open an LLM span — show the prompt, completion, model, tokens.
Phoenix is LLM-first. Same trace, different UI. See the actual prompt we sent, the completion, token counts, latency. This is with OTEL_PRIVACY_LEVEL=debug on this VM. Production or prod-like tenants run at observability tier — same span structure, no content attributes.

Point out the 9-signal consensus (intake trace)

Find an intake trace (POST to /api/v1/admin/uploads/{id}/reextract). Show arion.consensus.run → 9 signal spans + aggregate + arbitrate.
This is extraction. Nine signals: explicit refs, doc mappings, fingerprint keywords, semantic top-K, BM25 lexical, per-protocol scope, content shape penalty, semantic fit gate, evidence uniqueness. Candidates need corroboration to auto-accept. A bounded LLM arbiter adjudicates the middle band — cannot invent, cannot override auto-accept. 42% recall lift over the prior LLM-only pipeline; cross- framework findings surface directly.

Fallbacks if something breaks

SymptomFix
Chat takes 30 seconds on first shot You forgot to warm the cache. Fire the pre-demo curl command, wait ~30s, then subsequent chats are 4-7s. Recover by explaining "posture cache misses cost — see Ship 45'.c retro".
Jaeger UI empty sudo systemctl restart arioncomply-jaeger — wait ~5s, refresh.
Phoenix UI empty sudo systemctl restart arioncomply-phoenix — wait ~10s, refresh.
API returns 500 Check /tmp/api.log. If RAG pipeline failed, verify Chroma is on port 8000: lsof -i :8000 should show a chroma process, not python3 http.server. Restart Chroma: nohup /home/arionlabs/.local/bin/chroma run --host 127.0.0.1 --port 8000 --path /data/arioncomply/chroma_db > /tmp/chroma.log 2>&1 &
Chat conversation gone after reload Verify window.ARION_JS_VERSION in browser console prints 2026-07-26-chat-persistence. If not, hard-reload (Cmd+Shift+R or Ctrl+Shift+R).
Dashboard shows nothing API key: check the top-right corner has the correct key filled in (default: arion_dev_key_2026). Click Connect.
