ArionComply — Customer Host Prep Checklist

Everything you need to do BEFORE your Claude operator connects to install ArionComply.
Customer-owned prep · pre-Claude handoff · 2026-08-29
DIY install (no operator) Architecture brief Demo walkthrough

This checklist covers your side of the deployment: provisioning the host (cloud VM or on-prem box), opening network paths, creating the operator SSH account, and packaging the handoff. Your ArionComply support engineer (Claude operator on their laptop) picks up from there.

The checklist is provider-agnostic. ArionComply installs identically on any Ubuntu 24.04 host — cloud VM, on-prem physical machine, or a VM under your hypervisor of choice. Two paths in this doc:

Path A · Cloud VM (Azure / AWS / GCP) Path B · On-prem / bare-metal

Step 1 differs per path; Steps 2-6 are the same for both. Path is called out only where the mechanics differ.

If you'd rather do the install yourself, see POC Install Guide — same host prep, different install path.

Path B · On-prem / bare-metal · you own the box

Install Ubuntu 24.04 from the ISO if the box isn't already running it. Anything meeting the spec table above works: dedicated server, workstation-class desktop, hypervisor VM (VMware, Proxmox, KVM), NUC-class mini-PC, or a Raspberry Pi–class device (see caveats below).

Network setup

  • Static IP recommended (either via DHCP reservation or a static config in /etc/netplan/). The operator will use this to SSH; it must not change mid-engagement.
  • The box must be reachable from the operator's laptop:
    • Same LAN: just a route from operator to the box's local IP
    • Different network: VPN (WireGuard, Tailscale, corporate VPN) with the operator as a peer, OR a reverse-SSH tunnel to a jump host
  • Outbound internet access for the install (see spec table). Firewalled outbound is OK if the four hosts above are on the allowlist.

Hardware caveats

  • ARM boxes (Raspberry Pi, Ampere): possible but not tested; Neo4j and Chroma have ARM builds. Expect a slower first-time Chroma reindex.
  • Older Intel CPUs (Haswell/Broadwell) work fine — install.sh doesn't require modern CPU features. Chroma reindex + Neo4j load will take longer (~1.5-2× a modern box).
  • Low-RAM boxes (<16 GB) will run into OOM during LLM calls under load; not recommended.
For evaluation only. On-prem PoC boxes rarely have the physical security posture (locked rack, audited access, hardware inventory) required for a production ArionComply install. Move to a hardened environment before any real compliance-program data lives on the box.

Step 2 · Configure firewall

Restrict inbound to SSH-from-operator-IP only. No public exposure of ArionComply's application ports (8080 / 8000 / 7474 / 7687) — those bind 127.0.0.1 and are accessed via SSH tunnel after install.

Path A · Cloud VM firewall · ~3 min

Add inbound rules in your cloud provider's console:

RulePrioritySourcePortAction
SSH — operator1000Operator's public IP /3222Allow
SSH — you (optional)1010Your public IP /3222Allow
Deny all inbound4096AnyAnyDeny (default)

Provider mechanics:

  • Azure — edit the auto-created NSG (<vmname>-nsg)
  • AWS — edit the VPC security group attached to the instance
  • GCP — add VPC firewall rules with a network tag applied to the instance

Confirm operator's public IP with them before setting the rule. They can find it via curl ifconfig.me on their laptop.

Path B · On-prem firewall · ~2 min

Configure ufw (Ubuntu's default) on the box itself:

sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow from <operator-lan-ip> to any port 22 proto tcp
# Optional: your own admin access
sudo ufw allow from <your-lan-ip> to any port 22 proto tcp
sudo ufw enable
sudo ufw status verbose

If the box sits behind a corporate firewall / router, apply the equivalent rule at that boundary too — the operator connects from OUTSIDE the box; whatever gateway lives between them and the box must forward SSH.

Do not open :8080, :8000, :7474, or :7687 to the network. ArionComply services bind to 127.0.0.1 and are accessed via SSH tunnel after install. If you want a browser experience, tunnel from your laptop:
ssh -L 8080:127.0.0.1:8080 <your-user>@<host-ip>
Then open http://127.0.0.1:8080/ui/arioncomply.html.

Step 3 · Create the operator user

SSH to host as your admin user · ~2 min

Create a dedicated arionops sudo user for the operator:

# Get the operator's SSH public key from them (as a file or text block)
# Example: their key looks like  ssh-ed25519 AAAAC3... arionops@laptop

sudo adduser --gecos "" --disabled-password arionops
sudo usermod -aG sudo arionops

# Passwordless sudo (recommended for automation)
echo 'arionops ALL=(ALL) NOPASSWD:ALL' | sudo tee /etc/sudoers.d/arionops
sudo chmod 440 /etc/sudoers.d/arionops

# Install the operator's SSH pubkey
sudo mkdir -p /home/arionops/.ssh
sudo chmod 700 /home/arionops/.ssh
echo '<paste operator pubkey>' | sudo tee /home/arionops/.ssh/authorized_keys
sudo chmod 600 /home/arionops/.ssh/authorized_keys
sudo chown -R arionops:arionops /home/arionops/.ssh

Passwordless sudo is convenient for automation. If your policy requires interactive sudo, that's OK too — the operator will handle password prompts.

Never share your admin user's SSH key with the operator. The operator's key exists only on their laptop; you install their public key on the host. If you rotate the operator user later, just remove the entry from /home/arionops/.ssh/authorized_keys.

Step 4 · Prepare the install directory

Still SSH'd as admin · ~1 min
sudo mkdir -p /data/arioncomply
sudo chown arionops:arionops /data/arioncomply
ls -ld /data/arioncomply
# Expected: drwxr-xr-x arionops arionops ... /data/arioncomply

The operator's install.sh will populate this directory — you don't need to pre-clone anything.

Step 5 · Choose a secret-delivery channel

Coordination · ~10 min upfront

After install, the operator provisions your first tenant, which produces an API key printed once. That key is hashed at rest on the host — there's no way to retrieve it later. You need a plan for how the operator delivers it to you.

Acceptable channels

  • Shared vault in a password manager (1Password, Bitwarden, LastPass, etc.) — recommended
  • Your organization's secret-management platform (HashiCorp Vault, AWS/Azure/GCP secrets managers)
  • End-to-end encrypted messaging with disappearing messages (Signal, Wire) — acceptable if company policy allows

NOT acceptable

  • Email — plaintext across mail servers, retained forever
  • Slack / Teams / Discord — logs retained, not designed for secrets
  • SMS / WhatsApp — not audited or E2E-secure for enterprise data
  • Any handback report PDF or text file — the operator's runbook explicitly forbids this

Tell the operator upfront which channel you'll use. Give them the specific vault/vault-item address they should write to. They'll confirm receipt with you.

Step 6 · Send handoff to the operator

Package · ~2 min

The operator needs these to start:

  • Host address — public IP or hostname for cloud VMs (e.g. 40.68.12.34); LAN IP + connection method for on-prem (e.g. 10.0.1.85 reachable via WireGuard peer)
  • Operator SSH user (arionops, or whatever you chose in Step 3)
  • Confirmation Step 2 firewall rule is live — screenshot or written "SSH from your IP is allowlisted"
  • Which OS you installed (Ubuntu 24.04 or 22.04) so they know the expected package set
  • Deployment path (cloud provider name, or "on-prem") — helps the operator anticipate provider-specific gotchas or on-prem gotchas (proxy, DNS, corporate CA)
  • Postgres passwords — either you pick two strong passwords (owner + app roles) and share via the same secret-vault as Step 5, or you tell the operator "you pick, store in vault, and give me the pointer"
  • Neo4j password — same pattern as Postgres
  • OpenAI API key (or the equivalent LLM provider key) — you provide, ideally as a scoped throwaway with a monthly billing cap set BEFORE sending. Share via secret-vault.
  • Secret-delivery channel details from Step 5 — vault name + item address the operator writes to
Send the connection info (host + user + path) via any normal channel — email/chat is fine, this isn't secret. Send passwords + API keys via the secret-vault only. Same rule applies to their handback: tenant API key comes back through the vault, not through email.

What happens next (operator's side)

Once you've handed off, the operator will:

  1. Verify SSH access + host readiness
  2. Clone the ArionComply repo into /data/arioncomply
  3. Run install.sh --yes with the credentials you supplied (~15 min cloud, ~20-25 min older on-prem hardware)
  4. Verify all 4 services healthy via arion_status.sh --json
  5. Provision your first tenant + capture the API key
  6. Smoke-test end-to-end (deployment status, chat, SPA)
  7. Deliver the tenant API key to your secret-vault
  8. Send you a handback document with health report + next-step instructions

Full runbook they follow: CLAUDE_OPERATOR.md in the repo. You don't need to read it, but it's there if you want to know what they're doing.

Ongoing support

Post-handback · reference

After handback, both you and the operator can produce diagnostic bundles when things break:

ssh arionops@<host> 'bash /data/arioncomply/scripts/ops/diagnose.sh'
# → prints path to /tmp/arion-diag-<host>-<timestamp>.tar.gz
scp arionops@<host>:/tmp/arion-diag-*.tar.gz ./

Send the bundle to the operator when opening a support ticket. It contains no evidence text, chat prose, LLM content, or raw API keys — safe to share. See Error Catalog for common ARION-* codes and their fixes.

If you want to rotate the operator user (end of engagement, personnel change, etc.):

# Revoke the operator's SSH key
sudo sed -i '/<operator-key-comment>/d' /home/arionops/.ssh/authorized_keys

# Or fully remove the user
sudo userdel -r arionops
sudo rm /etc/sudoers.d/arionops

Uninstall

Full removal (yours to run when the PoC ends):

# Stop + disable services
sudo systemctl stop arioncomply-{api,chroma,jaeger,phoenix} 2>/dev/null
sudo systemctl disable arioncomply-{api,chroma,jaeger,phoenix} 2>/dev/null
sudo systemctl stop arioncomply-sweep.timer 2>/dev/null
sudo systemctl disable arioncomply-sweep.timer 2>/dev/null

# Remove systemd units
sudo rm /etc/systemd/system/arioncomply-*.service /etc/systemd/system/arioncomply-*.timer
sudo systemctl daemon-reload

# Databases
sudo -u postgres dropdb arioncomply_compliance
sudo -u postgres dropdb arioncomply_sessions
sudo -u postgres dropuser arioncomply_app
sudo -u postgres dropuser arioncomply

# Application files
sudo rm -rf /data/arioncomply

# Neo4j (optional — leave if reused for other apps)
sudo apt purge neo4j
sudo rm -rf /var/lib/neo4j /etc/neo4j

The operator user (arionops) is yours to keep or remove independently — the checklist steps above show how to revoke or delete the account.
