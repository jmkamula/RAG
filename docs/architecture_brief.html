ArionComply

Compliance Program Ledger · Architecture & Innovation Brief · 2026-07-26

ArionComply is a compliance program ledger, not a generic evidence repository. Our role: track where evidence lives, its freshness, its ownership, and its auditor-readable provenance — while the tenant keeps evidence sovereignty in the systems that already hold their data (Odoo HR, Okta IAM, ServiceNow CMDB, document workflows).

Under the hood, it is a cross-platform Retrieval-Augmented Generation stack purpose-built for compliance: a role-aware graph of requirements, a deterministic case-file & preservation-check discipline for LLM answers, a nine-signal consensus extractor for evidence discovery, and a dual-backend OpenTelemetry stack to make every decision observable.

2.1 Datastore choices — and why

StoreRoleWhy this & not X
Neo4j Requirement graph, role model, cross-framework edges (DEMONSTRATES, IMPLEMENTS, SUPPORTS...) Compliance is fundamentally a graph problem: an obligation like GDPR Art. 35 DPIA is demonstrated by an ISO 27701 A.7.2.5 program leaf that itself satisfies ISO 27001 6.1.2. Relational joins would mask the semantics.
Postgres Posture, findings, evidence, tenant state, RLS-scoped multi-tenancy Tenant isolation via Row-Level Security is battle-tested. Every auditor-load-bearing table (posture_controls, document_findings, posture_status_log) is here, with append-only compliance semantics where auditors need them.
ChromaDB Semantic embeddings for query → requirement retrieval; per-framework collections Purpose-built for RAG. One embedding model (text-embedding-3-large) across all four collections after Ship 5' consolidation. Retrieved via consensus signals, not raw top-K.
Jaeger + Phoenix Distributed tracing: Jaeger for infrastructure spans, Phoenix for LLM-first UI Both consume OTLP; SDK exports to both in parallel. Traces are portable to any OTel-native backend (Grafana Tempo, Honeycomb, Langfuse) without rewrites.

3. Breakthrough innovations

3.1 Ship 2' Case-file discipline: bounded LLM + APPEND-ONLY preservation-check

The chat pipeline gives the LLM a compact case-file digest (~450–650 tokens: query, posture, cited refs, cross-framework bridges, session context) rather than the pre-Ship-2' 21,731-token average prompt. After the LLM answers, a preservation-check runs deterministically: every required ref, [DRAFT] tag, verdict prefix, and cross-framework bridge line that the LLM was expected to include is verified. Missing elements are appended as a footer — never rewriting LLM prose. This means:

  • The LLM cannot silently drop compliance-load-bearing facts. If it did, the deterministic repair pass restores them.
  • The LLM cannot invent controls or refs. The digest is the only ground truth; the repair pass only preserves, never adds.
  • Auditor safety by construction. No stochastic decision is compliance-load-bearing.

3.2 Ship 32-43 Nine-signal extraction consensus

Evidence extraction from tenant documents runs a nine-signal consensus similar in spirit to the chat pipeline, with signals ordered by compliance-authority (highest first):

Signal Weight What it captures ────────────────────────── ────── ───────────────────────────────── explicit_ref 1.00 doc verbatim cites "A.5.15" or "Art.32" doc_mappings_target 0.60 curator-authored filename → leaf map fingerprint_keyword 0.50 Ship 28/29 exact-token-set catalog must_semantic_topk 0.30 Chroma embedding top-K bm25_topk 0.25 lexical relevance (Ship 43) per_protocol_scope 0.10 per-standard Chroma retrieval semantic_fit_gate ±0.30 post-fingerprint cosine verifier content_shape_penalty −0.50 sentence looks like a field/header evidence_uniqueness −0.50 cross-candidate anti-multi-attribution

Candidates need corroboration (2+ signals) to auto-accept; a bounded LLM arbiter (cannot invent, cannot override auto-accept) adjudicates the middle band. Result on Arion demo across 5 baseline docs: +42% recall vs pre-arc, and cross-framework GDPR findings surface directly (Art.35 on a DPIA doc) where the previous LLM discovery pipeline missed them entirely.

3.3 Ship 40 Framework role model: obligations & demonstrators

Frameworks are not siblings. ISO 27001 is a program; ISO 27701 is an extension of ISO 27001; GDPR is a set of obligations demonstrated by programs & extensions; ISO 27003/4/5 is guidance. Edges in Neo4j encode which programs DEMONSTRATE which obligations. Posture propagates: if A.7.2.5 (ISO 27701 privacy risk assessment) is Comply, then Art.35 (GDPR DPIA) posture materialises via the _apply_demonstrates_overlay at posture-load time — without duplicating evidence.

3.4 Ship 42 Two-view semantics: engine vs. auditor UI

Same table, two views. Engine reads per-MUST rows for checklist_item_id = ANY(...) recognition (needs N rows for N MUSTs). Auditor UI wants 1 row per unique (excerpt, control_ref). Ship 42 resolved the tension with an evidence_group_id column stamped at write, and surface-layer queries doing DISTINCT ON (evidence_group_id). Persistence stays engine-friendly; the auditor sees clean single-citation views. 60% reduction in Stage-1 queue visual size after backfilling legacy rows.

3.5 Ship 44 Dual-backend OTel: Jaeger + Phoenix

Every request, DB query, LLM call, LangGraph node, consensus signal, posture load, and preservation-check event is a span. Two backends consume the same OTLP export:

  • Jaeger for general trace waterfalls, service map, dependency graph.
  • Arize Phoenix for LLM-first UI: prompt/completion viewer, RAG evaluation-ready.

Spans use the emerging OpenTelemetry Semantic Conventions for GenAI (gen_ai.*) so traces are portable to Grafana Tempo, Honeycomb, Langfuse, or any OTel-native backend. A 3-tier privacy env (OTEL_PRIVACY_LEVEL={off, observability, debug}) gates whether content attributes (LLM prompts, evidence excerpts, chat query text) are captured — safe by default.

3.6 Ship 45 N+1 fix via batched EvalContext + TTL cache

Ship 44's tracing revealed that the chat's retrieve node spent 79% of its latency in two nested per-ref loops (build_related_cards and build_templates_block), each rebuilding an EvalContext (Postgres + Neo4j scan) + fresh Neo4j session + fresh spec resolver per call. Ship 45 batched via build_advisory_data_for_refs (shared context across all refs in one call) plus a 30-second TTL cache on the invariant Neo4j _load_er_evidence_types scan. Result on the deterministic posture-enumeration path: chat latency 11.7s → 7.3s (-37%); 2290 → 1169 SELECTs (-49%).

4.3 Phoenix — where LLM interactions are inspected

Every OpenAI SDK call auto-instruments via OpenInference and lands in Phoenix with the OTel GenAI semantic conventions: model, input+output tokens, latency, and (in debug tier) prompt+completion content. Phoenix groups them per LLM call so you can see:

  • What the case-file digest sent to the LLM (~2k tokens)
  • What the LLM returned (structured JSON via response_format={"type": "json_object"})
  • The consensus arbiter's per-candidate LLM decisions
  • Chroma queries (auto-instrumented via httpx)
